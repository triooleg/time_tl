# WEATHER-GEO-01 — погода, покрытие и меню

05.11.2026: LOCAL integration. Production не изменялся. Последнее
пользовательское дополнение отменяет обязательный сбор погоды по всей стране:
нужны только точки и группы, для которых есть фактический пользовательский спрос.

## Реализовано

- Меню в двух колонках: «Мій день / Мої календарі», «Розклад / Домашні завдання»,
  «Електроенергія / Погода», «Налаштування / Допомога». Выключенные функции
  не создают пустых рядов; счётчик ДЗ сохраняется.
- Общий PostgreSQL read model `ActiveGeographicCoverage` восстанавливается из
  фактических подписок. Отдельной изменяемой таблицы счётчиков нет. Территория
  тревог и оператор электричества не отождествляются по названию или UID.
- Power collector запрашивает только востребованные подтверждённые области;
  из полного ответа сохраняет только выбранные группы. После ожидания квоты,
  перед HTTP и при записи спрос перепроверяется. Нулевой спрос не вызывает HTTP.
- MET Norway: один прогноз на статическую точку, 4/6 циклов по Киеву,
  условный HTTP, устойчивые к рестарту Retry-After и HTTP Expires. Срок
  пригодности прогноза отделён от HTTP-кеша. Контакт — реальный URL репозитория.
  Новые точки и ручной запрос используют ту же фоновую очередь и лимиты.
- Почасовые значения, версии по хешу и события хранятся централизованно.
  Отсутствующие параметры остаются неизвестными. Осадки за шесть часов
  не делятся искусственно на часы.
- Telegram читает локальную БД. Получение прогноза отделено от согласия на
  уведомления, мастер которых выключен по умолчанию. Есть прогнозные карточки,
  время/категории/заблаговременность, полное отключение. Область не подменяется
  прогнозом областного центра. При выключенном сборе интерфейс это сообщает.
- Детерминированный planner объединяет рекомендации, различает ожидаемое
  событие, корректировку и отмену. Корректировка требует истории доставки.
  Прогноз не выдаётся за наблюдение или официальное предупреждение;
  атрибуция MET сохраняется.
- Существующий outbox/sender повторно проверяет территорию, согласие, версии,
  свежесть и относящиеся к сообщению факты. Приоритет тревог перепроверяется
  между сообщениями по свежему времени. Неопределённая доставка блокирует
  повтор по идентичности события/дате независимо от версии настроек.
  Безопасная отмена до первой попытки допускает новую неизменяемую генерацию;
  взятый payload не переписывается.
- Хранение настраивается: неиспользуемый кеш — 7 дней с наблюдаемой потери
  спроса, версии — 14 дней, история циклов/событий — 90 дней. Очистка ограничена,
  защищает pending-ссылки и не удаляет справочник территорий.
- Русская админка: `/settings/weather`, `/coverage`, `/settings/external-services`.
  Включение, частота, пороги, хранение, мониторинг, ручная очередь, один
  диагностический HTTP с общей квотой. Повторный пароль, CSRF, CAS, no-store.
- Существующие хранилища alerts.in.ua и Alerts Energy не дублируются. Пустой
  Energy API input сохраняет ключ; удаление требует отдельной отметки.
  Секреты не возвращаются, аудит не содержит их значений; generic settings
  не могут изменять приватное пространство `weather_`.

## Изолированная тестовая среда

Добавлена **не применённая к production** миграция `0012_weather_coverage`
после `0011_power_outages`, семь таблиц. Схема заморожена; частичное или
несовместимое предсуществующее состояние отклоняется. Backup inspector
поддерживает head12 без изменения старого шифрования, ключа, AAD и контрактов
старых резервных копий. Компиляция DDL не доказывает реальную миграцию/restore.

Для отдельной LOCAL/test PostgreSQL после миграции на head12:

1. Проверить и импортировать статический CSV через `db/weather_locations.py`:
   HTTPS-источник, SHA-256 исходных байтов, версия, автор и время проверки;
   точное совпадение КАТОТТГ и active provider UID. При смене координат или
   происхождения создаётся новый UUID точки.
2. Включить `WEATHER_ADMIN_ENABLED` и `WEATHER_ENABLED`; явно принять условия
   MET и проверить контакт через админку. Само включение админки не разрешает
   фоновую отправку. По умолчанию все новые флаги выключены.
3. `python -m time_tl.runtime.weather_service`: отдельный DB-only процесс без
   Telegram/API/signing ключей и `.env`. `--check` проверяет только
   nonproduction среду/схему. Сборщик использует singleton lease.
4. Planner: `python -m time_tl.runtime.weather_notification_service` с
   `WEATHER_NOTIFICATIONS_ENABLED=true`; отправляет существующий sender.
   SIMULATION использует подставной транспорт. Живой STAGING требует
   отдельного разрешения и allowlist.
5. `DYNAMIC_COVERAGE_ENABLED` включает новую оптимизацию power collector.
   Историческое поведение при выключенном флаге сохраняется.

Старые production attestation/head9/head10 не авторизуют этот этап. Новые
погодные роли/флаги в production программно закрыты до нового рассмотренного
релиза. Изменением ENV или сохранением формы этот запрет не снимается.

## Неполученные доказательства

- Проверенный каталог координат пока не импортирован. См.
  [GEODATA-RESEARCH.md](GEODATA-RESEARCH.md): OSM-кандидат требует проверки
  географии, происхождения и ODbL; государственным источником он не объявлен.
- Open-Meteo представлен закрытой границей допуска, не готовым runtime
  адаптером. Допустимый бесплатный режим/платный интерфейс не подтверждены.
  NOAA/DWD/ECMWF, Meteoalarm и Укргидрометцентр не подключены. Авто-fallback нет.
- Полный snapshot alerts.in.ua и state machine не менялись. Coverage — модель
  спроса, а не разрешение отбоя.
- Нужны native Linux/PostgreSQL migration/restore/race проверки в отдельной
  лаборатории, затем разрешённый погодный staging canary. Офлайн ORM fixtures
  не являются доказательством PostgreSQL или production.
- Нового разрешения на production migration/secrets/deployment нет. Рабочие
  API, Telegram, сервер, пароли, ключи и Git remote не изменялись.
